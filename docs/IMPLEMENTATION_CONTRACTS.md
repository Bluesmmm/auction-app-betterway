# 实现级契约

本文档记录可直接约束代码、数据库、API、队列、权限和测试的实现契约。它不是产品需求扩写，也不是架构愿景；每条契约都应能落到实现和验收。

## 1. 契约主线

第一组实现级契约以“最小拍卖闭环”为中心：

```text
家长/孩子身份
  -> 加入社区
  -> 提交拍品
  -> 审核通过
  -> 创建拍卖
  -> 出价冻结
  -> 结束结算
  -> 家长确认
  -> 交付确认
  -> 积分转移
```

第一版不以页面数量、后台功能完整度或全量治理能力作为主线，而以这条闭环能否稳定通过事务、状态、权限和账本验证作为主线。

## 2. 外部能力契约

第一版允许使用 fake/mock provider 支撑开发和自动化测试，真实外部服务后续按同一 provider contract 替换。

适用外部能力包括：

- 微信登录。
- 微信手机号。
- 微信订阅消息。
- 文本和图片内容安全。
- OCR、二维码/条码识别和图片元数据检查。
- 对象存储和签名访问。

约束：

- fake/mock provider 只能替代外部调用，不能绕过核心业务规则。
- 核心业务事实仍只能由 PostgreSQL 裁决。
- provider 调用失败、超时、不可解析或结果冲突时，业务默认失败关闭。
- 通知 provider 失败不能改变拍卖、交易或积分事实。
- 对象存储 provider 必须保持“私有对象、短期授权、可撤销访问”的行为边界，即使第一版使用本地或 mock 实现。

## 3. 账号与身份契约

第一版采用统一内部用户主体：

- `users` 表示内部登录主体。
- 微信身份绑定到 `users`，不直接等同家长或孩子。
- 家长能力由 `guardian_profiles` 和有效监护关系决定。
- 孩子参与能力由 `child_profiles`、有效监护关系、社区成员状态和家长控制项共同决定。
- 同一 `users` 记录可以在不同上下文下具备不同 profile 或 scope。

约束：

- 不创建 `parent_users`、`child_users` 两套账号主体。
- 权限判断不得只依赖登录用户类型，必须显式校验当前用户是否能代表目标孩子执行目标动作。
- 所有孩子侧写操作必须显式携带目标 `child_id`，不能依赖客户端本地缓存的“当前孩子”。
- 审计日志必须记录操作者 `user_id`、目标 `child_id` 或管理 scope，以及服务端裁决时间。

## 4. 主监护人失败关闭契约

最小拍卖闭环必须依赖有效主监护人。

无有效主监护人的孩子档案可以存在于引导或待绑定状态，但不能参与拍卖社区内的业务闭环。

阻断范围：

- 加入社区。
- 提交拍品。
- 提交求购。
- 响应求购。
- 出价。
- 成交确认。
- 交付确认。

无有效主监护人的情形包括：

- 孩子微信登录但尚未绑定家长。
- 家长创建孩子档案但尚未完成监护声明或儿童信息授权。
- 主监护人关系被撤销、限制、关闭或进入争议冻结。
- 主监护人账号疑似被盗且敏感能力被暂停。
- 只有副监护人但没有有效主监护人。

约束：

- 服务端必须在每个孩子侧写操作中校验有效主监护人。
- 客户端只能展示引导、查看允许的非敏感信息或错误状态，不能自行降级放行。
- 已在途拍卖、冻结积分或交易遇到监护争议时，必须进入冻结或平台复核路径，不能继续自动成交、确认或转积分。

## 5. 社区准入契约

第一版社区加入必须完整保留三步准入：

```text
invite_code_validated
  -> guardian_confirmed
  -> admin_approved
  -> community_member_active
```

约束：

- 邀请码只能创建或推进加入申请，不能直接产生 active 社区成员。
- 家长确认必须发生在孩子获得社区参与能力之前。
- 活动管理员审核通过后，成员状态才可变为 active。
- 只有 active 社区成员可以浏览、搜索、提交拍品、提交求购、响应求购、出价、收藏或关注社区内容。
- 邀请码使用次数以服务端事务内的原子消耗结果为准。
- 活动管理员权限必须受社区 scope 限制，不能跨社区审核、搜索、导出或查看儿童数据。

## 6. 内容版本与审核契约

第一版拍品、求购、求购响应以及其他孩子端可见公开内容必须采用内容版本模型。

模型关系：

- `items`、求购和响应等表表示业务对象。
- `content_versions` 表示一次可审核、可展示、可追溯的公开内容快照。
- `moderation_tasks` 必须绑定具体 `content_version_id`。
- 业务对象的 `current_public_version_id` 只能指向已审核通过、允许公开展示的内容版本。
- 业务对象的 `latest_version_id` 可以指向待审核、审核中或被拒绝的新内容版本。

约束：

- 标题、描述、图片、瑕疵说明、分类、交付说明和其他孩子端可见文本修改后，必须创建新内容版本并重新审核。
- 审核决定只对绑定的内容版本有效，不能复用到后续修改版本。
- 新版本审核通过前，孩子端继续展示上一已审核版本。
- 若不存在上一已审核版本，则孩子端不展示该业务对象。
- 新版本命中高风险或严重风险时，服务端必须按风险规则隐藏、下架或转平台复核，不能继续无条件依赖旧版本展示。
- 审计、下架、申诉、举报和后台复核必须能追溯到当时公开展示的内容版本。

## 7. 拍卖场次与固定时长契约

拍卖排期不是孩子或家长可配置能力。

创建规则：

- 拍品内容版本人工审核通过后，系统按社区默认固定拍卖时长创建拍卖场次。
- `start_at` 必须使用服务端或数据库裁决时间。
- `end_at` 必须由 `start_at + community.default_auction_duration_minutes` 得出，不能由客户端提交。
- 若社区未开放或平台治理开关暂停，拍卖场次不得进入可出价状态。

约束：

- 孩子和家长不能自定义拍卖开始时间、结束时间或持续时长。
- 客户端只能展示服务端返回的拍卖时间，不能基于本地时间裁决状态。
- 授权管理员可以调整单个拍卖场次结束时间，但必须填写原因、写入审计日志，并执行影响预览和二次确认。
- 已有出价后的结束时间调整属于高风险操作，必须受更严格限制，并通知当前最高出价方、卖家家长和关注者。

调整权限：

- 活动管理员可以调整自己管理社区内的拍卖场次结束时间。
- 平台管理员可以复核异常调整、处理投诉、执行治理下架或进行兜底修正。
- 社区创建者只有在具备有效活动管理员身份时，才可按活动管理员权限调整。
- 孩子、家长、主监护人、副监护人不能调整拍卖排期。
- 调整行为异常频繁时，必须进入平台复核或风险告警。

## 8. 出价与冻结契约

第一版只支持具体积分出价，不支持自动代理出价。

出价规则：

- 客户端提交的是明确的 `amount_points`。
- 新出价必须大于等于 `current_price_points + min_increment_points`。
- `amount_points`、`start_points`、`min_increment_points` 必须是正整数，并受平台配置上限约束。
- 小程序可以提供快捷加价按钮，但服务端只接受明确积分金额。
- 不存在最高心理价、自动追价或系统代理加价。

冻结规则：

- 每个拍卖场次最多只有一个当前最高出价。
- 只冻结当前最高出价者的积分。
- 新出价成功时，旧最高出价者积分必须在同一事务内解冻，新最高出价者积分必须在同一事务内冻结。
- 被超越的旧出价记录保留历史，但不再持有 active 冻结。

裁决规则：

- 出价成功只能由 PostgreSQL 事务结果裁决。
- Redis、防重复点击、WebSocket、本地页面状态和客户端时间都不能裁决出价成功。
- 事务超时、锁等待超时、死锁重试耗尽、网络中断或结果不确定时，服务端不能返回业务成功；客户端必须刷新拍卖和积分状态。

出价资格硬拦截：

- 卖家孩子和出价孩子是同一个 `child_id`。
- 卖家孩子和出价孩子拥有同一个 active 主监护人。
- 卖家孩子和出价孩子的主监护人手机号哈希相同。
- 卖家孩子或出价孩子处于未解决监护争议冻结状态。

风险信号但不自动硬拦截：

- 相同设备。
- 相同 IP 或异常网络。
- 异常夜间活跃。
- 短时间异常浏览、收藏或出价。
- 跨社区异常加入。

上述风险信号应进入风控记录或平台复核，不作为第一版同家庭互拍硬判定。

## 9. 成交、确认与积分转移契约

拍卖结束不等于积分转移。

结束规则：

- 拍卖结束时无有效出价，拍卖场次进入流拍状态。
- 拍卖结束时有有效最高出价，拍卖场次进入成交后的家长确认流程。
- 最高出价者积分继续冻结，不立即转给卖家。

确认规则：

- 买卖双方家长确认前，不转移积分。
- 第一版成交确认必须由买卖双方孩子的有效主监护人完成。
- 第一版交付确认必须由买卖双方孩子的有效主监护人完成。
- 副监护人可以查看、接收提醒或协助沟通，但不能替代主监护人做成交确认、拒绝、交付确认或拒绝。
- 任一方家长拒绝或确认超时规则判取消时，冻结积分释放给买家。
- 双方家长确认后进入交付确认阶段，积分仍继续冻结。
- 双方交付确认后，买家冻结积分转移给卖家可用积分。
- 申诉或争议期间，积分继续冻结，直到管理员按允许路径处理。

成交确认超时规则：

- 拍卖结束后进入 `pending_guardian_confirm`。
- 买家主监护人和卖家主监护人都有 48 小时确认窗口。
- 48 小时内任一方拒绝时，交易取消，买家冻结积分解冻。
- 48 小时到期时，只要任一方未确认，交易取消，买家冻结积分解冻。
- 不支持单方确认即进入交付。
- 不支持超时默认同意。
- 管理员可以在超时前介入暂停或延长，但必须填写原因并写入审计日志。

交付确认超时规则：

- 双方主监护人完成成交确认后，交易进入 `pending_delivery_confirm`。
- 交付确认窗口为 72 小时。
- 72 小时内双方主监护人都确认交付完成时，积分从买家冻结积分转移给卖家可用积分。
- 72 小时内任一方发起申诉时，交易进入 `disputed`，积分继续冻结。
- 72 小时到期时，只要任一方未确认，交易进入管理员处理队列。
- 交付确认超时不自动转积分。
- 交付确认超时不自动取消交易。
- 管理员处理结果只能影响平台内状态和积分，例如继续冻结、取消并解冻、确认转移；不裁决线下赔偿。

交付争议裁决动作：

- `release_to_buyer`：取消交易，买家冻结积分解冻。
- `transfer_to_seller`：确认完成，买家冻结积分转给卖家可用积分。
- `keep_frozen_for_platform_review`：继续冻结，升级平台管理员复核。

第一版不支持：

- 部分转积分。
- 平台额外赔积分。
- 扣双方积分作为处罚。
- 裁决人民币补差价。
- 记录线下赔偿金额。
- 把积分转给第三方。

约束：

- 成交状态、交易状态和积分流水必须在同一业务事务边界内保持一致。
- 积分转移必须通过不可变账本流水表达，不能直接改余额后缺失流水。
- 管理员裁决只处理平台内状态和积分，不裁决线下赔偿。

## 10. 积分账本契约

第一版积分系统必须使用不可变账本流水和余额快照，不能只存余额字段。

模型关系：

- `point_accounts` 保存每个孩子档案的 `available_points` 和 `frozen_points` 快照。
- `point_ledger_entries` 追加记录所有积分发放、冻结、解冻、转移和冲正。
- `point_holds` 记录与拍卖或交易相关的冻结生命周期。

约束：

- 余额快照和账本流水必须在同一数据库事务中更新。
- 账本流水不能更新或删除。
- 账务错误只能通过追加冲正流水修正。
- 冻结、解冻、转移、管理员调整等关键动作必须具备 `idempotency_key`。
- 账户余额不得为负。
- 当前最高出价对应的 active 冻结必须可追溯到具体拍卖场次和出价记录。
- 系统必须提供账本校验任务，用流水重算并核对余额快照。

初始积分：

- 孩子档案完成主监护人绑定并首次激活时，系统发放一次初始积分。
- 初始积分数量来自平台配置，例如 `initial_child_points`。
- 一个孩子档案只能领取一次初始积分。
- 初始积分发放必须写入 `point_ledger_entries`，类型为 `initial_grant` 或等价枚举。
- 孩子档案关闭后重新打开，不再次发放初始积分。
- 管理员后续加减积分必须走管理员调整流程，不能伪装成初始发放。

管理员积分调整：

- 活动管理员不能直接调整积分。
- 平台管理员可以创建积分调整请求。
- 小额、单个孩子、非争议场景的调整可以由单个平台管理员执行。
- 批量调整、大额调整、争议相关调整、冲正历史错误必须由第二个平台管理员复核。
- 所有管理员积分调整必须填写原因、写入审计日志并追加账本流水。
- 管理员积分调整不能直接修改余额快照而缺失账本流水。

## 11. 文件与图片访问契约

第一版文件和图片访问必须使用私有受控访问，不允许公开 CDN URL 作为业务展示入口。

生命周期：

- 上传后文件进入 `temp_private`。
- 未审核、审核中、拒绝、下架、删除或权限不匹配的文件不能生成可访问 URL。
- 审核通过后，文件可以转为 `formal_private`。
- 删除、下架、注销或权限变化后，旧授权必须失效或在访问网关被拒绝。

访问规则：

- 展示文件前，服务端必须校验当前用户、目标孩子档案、社区成员状态、内容版本可见性和文件状态。
- 鉴权通过后，只能生成短期签名访问或等价短期授权。
- 签名访问必须绑定文件、用户、用途和过期时间。
- 对象 key、签名 URL、存储桶内部路径不能出现在普通日志、通知正文、导出文件或客户端长期缓存中。
- fake/mock 对象存储实现也必须保持私有对象和短期授权边界。

## 12. 搜索、列表与可见性契约

第一版搜索、列表、热门、收藏和通知跳转都必须由服务端回源校验可见性后再返回客户端。

约束：

- 只有 active 社区成员可以搜索或浏览该社区内容。
- 搜索索引只能作为候选结果来源，不能作为最终可见性裁决依据。
- 热门、收藏、通知跳转和详情页同样不能绕过可见性校验。
- 未加入社区内容不能被全平台搜索发现。

返回客户端前必须回 PostgreSQL 校验：

- 当前孩子档案是目标社区 active 成员。
- 目标内容属于该社区。
- 目标内容未被下架、删除、拒绝或治理暂停。
- 目标内容展示版本等于 `current_public_version_id`。
- 目标内容版本已审核通过。
- 关联文件满足私有访问契约。

失败关闭：

- 搜索索引延迟、脏数据、旧数据或缓存命中时，仍必须回源校验。
- 回源校验失败时，不返回该内容。
- 可见性状态不确定时，不返回该内容。

## 13. API 写入响应契约

关键写 API 必须返回服务端裁决信息，不能只返回简单 `success: true`。

适用操作包括：

- 加入社区。
- 提交拍品、求购或响应。
- 审核通过、拒绝或升级复核。
- 出价、撤销、结算。
- 成交确认、交付确认、申诉。
- 管理员裁决。
- 积分冻结、解冻、转移、调整。
- 文件授权、下架、删除或撤销访问。

响应字段至少包含：

- `server_time`：服务端或数据库裁决时间。
- `target_type`：目标类型。
- `target_id`：目标 ID。
- `target_version`：目标业务版本。
- `latest_status`：服务端裁决后的最新状态。
- `result`：`accepted`、`rejected`、`pending`、`unknown` 或等价稳定枚举。
- `refresh_required`：客户端是否必须重新拉取状态。
- `error_code`：失败时的稳定错误码。

约束：

- 出价、结算、确认、交付、管理员裁决和积分调整必须返回服务端裁决后的最新状态。
- 事务超时、锁等待超时、死锁重试耗尽、网络中断或事务结果不明时，服务端不能返回业务成功。
- 结果不确定时，响应必须表达 `pending` 或 `unknown`，并要求客户端刷新目标状态。
- 客户端不能基于本地状态、客户端时间或 WebSocket 推送自行推导写操作成功。

## 14. 幂等键契约

关键写操作必须使用幂等键，防止弱网、重复点击、客户端重试、worker 重放或通知重试造成重复业务事实。

适用操作至少包括：

- 提交拍品、求购或响应。
- 上传确认和文件转正式。
- 加入社区申请。
- 出价。
- 撤销出价。
- 拍卖结算。
- 成交确认或拒绝。
- 交付确认或拒绝。
- 申诉提交。
- 管理员裁决。
- 积分调整。
- outbox 消费和通知发送。

幂等记录必须绑定：

- `idempotency_key`。
- 操作者。
- 动作。
- 目标类型和目标 ID。
- 请求摘要 `request_hash`。
- 首次处理结果或可回放结果引用。

处理规则：

- 同一个 `idempotency_key + actor + action + target + request_hash` 重试时，返回首次处理结果或当前等价结果。
- 同一个 `idempotency_key` 但请求摘要不同，必须拒绝为幂等冲突。
- 出价、结算、确认、交付、积分调整等关键事务中，幂等记录和业务状态必须在同一数据库事务内提交。
- 幂等键不能只存在客户端本地或 Redis 中，PostgreSQL 必须保留可审计记录。

## 15. Outbox 与通知契约

第一版所有外发通知和实时推送都必须从 outbox 派生，不能在业务事务中直接发送。

适用范围：

- WebSocket 推送。
- 小程序内通知。
- 微信订阅消息。
- 管理后台待办或提醒。
- 审核、成交、交付、申诉、积分异常相关通知。

约束：

- 关键业务事务内只写业务事实、审计日志和 `outbox_events`。
- 事务提交后，由 worker 消费 `outbox_events` 发送通知或推送。
- outbox 消费必须幂等，重复消费不能重复改变业务状态。
- 发送失败可以重试，并记录失败原因和下次可重试时间。
- 发送前必须回源校验接收人权限和目标最新状态。
- 通知正文不得包含儿童姓名、学校、地址、电话、二维码、微信号、快递信息、对象 key 或签名 URL。
- 通知发送成功或失败不能改变拍卖、交易或积分事实。

## 16. WebSocket 契约

WebSocket 只作为实时提示通道，不是业务事实源。

推送用途：

- 当前价变化。
- 出价被超越。
- 拍卖结束。
- 成交、确认、交付或申诉状态变化。
- 通知红点或待办提示。

事件字段至少包含：

- `event_id`。
- `server_time`。
- `target_type`。
- `target_id`。
- `target_version`。
- `event_type`。

客户端规则：

- 小程序关键状态以 REST 查询结果为准。
- 页面进入、恢复前台、出价后、通知跳转、WebSocket 重连后，必须 REST 拉取最新状态。
- WebSocket 事件可以更新轻量提示，但不能裁决出价成功、拍卖结束、成交确认、交付确认或积分转移。
- 乱序、重复、旧版本事件不能覆盖客户端已知较新状态。
- WebSocket 断线期间，客户端不能基于旧价直接出价，必须先刷新拍卖状态。

服务端规则：

- 连接加入房间前必须校验用户、孩子档案、社区成员状态和目标内容可见性。
- 权限变化、成员移除、家长解绑、账号限制、社区暂停或内容下架后，必须使相关连接失去访问能力。

## 17. 管理员危险操作契约

第一版管理员危险操作必须执行影响预览、二次确认和审计日志。

危险操作至少包括：

- 下架拍品。
- 取消拍卖。
- 调整拍卖结束时间。
- 释放冻结积分。
- 转移冻结积分给卖家。
- 暂停社区。
- 暂停新发布、出价或结算。
- 批量导出数据。
- 解除账号限制。
- 管理员积分调整。
- 处理交付争议。
- 删除或匿名化儿童数据。

影响预览：

- 执行前必须生成影响预览。
- 影响预览必须包含受影响拍卖、交易、冻结积分、通知对象、可回滚动作和潜在风险。
- 影响预览必须有过期时间。
- 二次确认时必须引用未过期的影响预览。

审计要求：

- 必须记录操作者、确认人、原因、服务端时间、影响摘要、前后状态和目标 scope。
- 活动管理员操作必须受社区 scope 限制。
- 平台管理员高风险操作必须支持复核、双人确认或冷却期。
- 审计日志不能记录敏感明文、对象 key 或签名 URL。

## 18. 状态机契约

核心状态机必须单独维护在 [STATE_MACHINES.md](./STATE_MACHINES.md)。

约束：

- 状态转换必须通过服务端显式 transition 执行。
- 未列出的状态转换默认禁止。
- 状态机表必须指导 TypeScript enum、数据库约束、service transition guard 和自动化测试。
- 每个状态机必须定义当前状态、下一状态、触发动作、操作者、guard、同事务副作用和失败关闭行为。
- `auction_session.status` 只表达拍卖竞价生命周期，不表达成交后的确认、交付或争议。
- 拍卖有最高出价并完成结算后，`auction_session.status` 变为 `settled`，并在同一事务内创建 `transaction.status = pending_guardian_confirm`。
- 成交后的确认、交付、争议和完成都由 `transaction.status` 表达。

## 19. 第一批自动化验收测试契约

第一批自动化测试以最小拍卖闭环和高风险失败关闭为主，不以页面级 E2E 覆盖率为主。

必须覆盖的 contract/integration tests：

- 无有效主监护人不能加入社区、发布、出价。
- 邀请码最后一个名额并发使用时，最多只有一个申请成功消耗名额。
- 未审核内容不展示。
- 修改公开字段后，新版本未审核通过前不展示新内容。
- 非 active 社区成员不能搜索或查看社区内容。
- 并发出价不会产生负余额或重复最高出价。
- 被超越后，旧最高出价者积分解冻。
- 拍卖结算幂等。
- 成交确认任一方拒绝或任一方超时，买家冻结积分解冻。
- 交付超时进入管理员处理队列，积分继续冻结。
- 交付争议三种裁决动作的账本结果正确。
- 旧签名 URL 在下架、删除或权限变化后不可访问。
- WebSocket 乱序或重复事件不改变最终业务状态。
- outbox 重试不重复改变业务状态。
- 账本快照可由流水重算并保持一致。

约束：

- 测试必须验证数据库事实，而不是只验证 API 返回文案。
- 涉及时间裁决的测试必须使用服务端或数据库时间控制方式。
- 涉及外部服务的测试使用 fake/mock provider，但不得绕过核心业务规则。
