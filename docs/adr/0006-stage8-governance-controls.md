# ADR 0006: Stage 8 Governance Controls Require Scoped High-Risk Authorization

## Status

Accepted

## Context

Stage 8 introduces governance controls for temporarily pausing or tightening risky business capabilities during pilot operations. The roadmap requires platform, community, and category-level controls; impact previews before dangerous administrative actions; scoped RBAC; MFA; audit evidence; and clear handling of active auctions, frozen points, pending transactions, and in-review content.

The existing codebase has community-scoped activity administrators, platform administrators, sensitive-operation challenges, high-risk admin operation previews, and risk restrictions. It does not yet have a dedicated governance control model or a single authorization boundary for creating and lifting these controls.

Treating governance controls as ordinary configuration would make it too easy for a scoped administrator to affect settlement, frozen points, and guardian transaction confirmation. Treating all controls as platform-only would slow down community-level incident response for publish, bid, and review pressure.

## Decision

Stage 8 governance control management is a high-risk administrative action with scoped authorization.

- Governance control management requires administrator MFA and a fresh sensitive-operation challenge.
- Stage 8 adds a dedicated sensitive operation type for governance control management instead of reusing the narrower `pause_community` operation.
- Governance controls use a dedicated fact instead of overloading risk restrictions or community status.
- Platform-scoped controls use a null scope id. Community-scoped controls must reference the target community.
- Creating a governance control is rejected when an active control already exists for the same scope and control type. The implementation must enforce this with database uniqueness, not only service-layer checks.
- Governance control creation requires a dedicated governance control preview. It must not reuse the narrower single-target high-risk operation preview contract.
- Governance control creation must strictly bind to an unexpired preview generated by the same actor for the same scope and control type. A preview can be consumed at most once.
- Lifting a governance control does not require a preview in the second-round implementation, but it still requires scoped authorization, administrator MFA, a fresh sensitive-operation challenge, a reason, audit evidence, and an outbox event.
- Platform administrators may create and lift platform-scoped and community-scoped governance controls.
- Activity administrators may only create and lift community-scoped controls for communities in their active `AdminCommunityScope`.
- Activity administrators may manage `pause_publish`, `pause_bid`, and `force_platform_review` controls for their scoped communities.
- `pause_settlement` is platform-admin-only because it affects frozen points, guardian transaction confirmation, and settlement closure.
- `institution_admin` is not allowed to manage governance controls in the Stage 8 second-round implementation because its authority boundary is not yet defined in the product language or code.
- Governance controls block subsequent actions by default. They do not automatically cancel auctions, delist content, release frozen points, adjudicate transactions, or rewrite existing business state.
- Stage 8 second-round guards cover publishing, bidding, settlement or guardian transaction confirmation, and activity-admin content approval under forced platform review. Search visibility, realtime hints, notifications, delivery-method controls, exports, and deletion workflows remain outside this decision.
- Stage 8 second-round work is not complete if it only creates governance-control records and admin UI. Each accepted second-round control type must have at least one real business write-path guard.
- `pause_settlement` blocks ordinary settlement and guardian transaction confirmation progress, including delivery confirmation where that shares the same transaction decision path. It does not block appeals, platform review, read-only governance views, ledger checks, or explicit platform-admin governance recovery actions.
- Creating or lifting a governance control emits an outbox event for observability and later fan-out. Stage 8 second-round implementation does not define the end-user notification matrix for those events.
- Stage 8 second-round admin UI extends the existing governance page with a focused controls tab for preview, create, list, and lift actions. It does not introduce a separate governance dashboard, category controls, export workflows, deletion workflows, provider governance, or two-person review UI.
- Stage 8 second-round guards evaluate active controls by status and time window. Controls whose end time has passed do not apply, but the implementation does not add an expiry worker that mutates those records to `expired`.

## Consequences

- Stage 8 can support community-level risk response without granting activity administrators direct settlement authority.
- The implementation must add a dedicated governance control fact and must not overload risk restrictions or community status for temporary operational controls.
- Business write paths must fail closed when an active governance control applies, while existing affected objects remain available for explicit later governance actions.
- Impact previews and audit logs must describe the existing affected surface so operators know what remains unresolved after a control is created.
- Category-scoped controls, delivery-method controls, export governance, deletion/anonymization, complaint anti-abuse, and provider governance remain later Stage 8 work unless separately decided.
- Verification must cover schema and migration contracts, preview expiry and impact summaries, scoped create and lift authorization, duplicate active-control rejection, publishing and bidding guards, settlement and transaction-confirmation guards, forced platform-review behavior, audit and outbox evidence, admin shell wiring, type checking, build, and the Stage 8 verification script.
